# Veriq Website — Codex Instructions

## Purpose

This repository is the production website for Veriq.

Veriq is a web design and development business based in Des Moines. The website exists to:

1. Clearly explain what Veriq does.
2. Establish credibility and trust.
3. Demonstrate the quality of Veriq's work.
4. Generate qualified project inquiries.
5. Support Veriq's local search presence.
6. Present the business as capable, intentional, modern, and professional.

This is not a generic agency template.

Treat the existing Veriq website as an established product and brand system. New work should extend and improve that system rather than repeatedly reinventing it.

The goal is not to make every section more decorative. The goal is to make Veriq clearer, more credible, more useful, and more effective at turning the right visitors into customers.

## Read This First

Before making substantial changes:

1. Inspect the relevant existing page and components.
2. Inspect shared layout, navigation, footer, typography, buttons, section patterns, and design tokens.
3. Inspect `package.json` before assuming framework versions, dependencies, or commands.
4. Search for an existing component or pattern before creating a new one.
5. Understand the purpose of the requested change before editing.
6. Preserve established Veriq conventions unless the user's task explicitly changes them.

Do not redesign the site from memory.

The current repository is the primary visual and technical source of truth.

## Source-of-Truth Rules

When information conflicts, use this order:

1. The user's current explicit instruction
2. Confirmed current Veriq business information
3. The current production-oriented repository implementation
4. Older copy, experiments, unused components, abandoned campaigns, or stale assets

Do not assume that old promotional language is still current simply because it exists somewhere in the repository.

Do not invent missing business facts.

If a change involves pricing, services, legal claims, guarantees, customer results, contact information, service areas, business credentials, promotions, or other meaningful public claims and the information is not confirmed, preserve the existing truth or report the ambiguity instead of guessing.

# Veriq Brand Principles

## 1. Veriq should feel intentional

The site should feel designed by a real studio with a point of view.

Prefer:

- Strong typography
- Deliberate hierarchy
- Generous but controlled whitespace
- Clear contrast
- Editorial composition
- Thoughtful asymmetry where appropriate
- Strong imagery or website work as visual proof
- Purposeful use of the brand accent
- Clean transitions between light and dark sections
- Simple interaction patterns

Avoid making Veriq look like:

- A generic SaaS startup
- A mass-produced agency template
- An AI website builder
- A cheap Fiverr-style service
- An over-designed experimental portfolio
- A corporate enterprise consultancy with inflated language

## 2. Preserve the established visual identity

Use the current implementation as the source of truth for exact values.

Broadly, Veriq's visual language includes:

- Warm off-white / neutral page surfaces
- Black and dark charcoal typography and sections
- Cyan / turquoise as the primary accent
- Bold condensed or display typography for major statements
- Clean, highly readable supporting typography
- Thin rules, borders, grids, and structured spacing where appropriate
- Strong black/white contrast
- Minimal decorative effects

The cyan accent should be intentional.

Use it for things such as:

- Primary calls to action
- Important emphasis
- Interactive states
- Small brand details
- Select labels or rules

Do not flood every section with cyan.

Do not introduce unrelated purple, blue-gradient, neon, glassmorphism, or trendy SaaS visual systems.

## 3. Command Attention is a philosophy, not decoration

"Command Attention" is part of Veriq's brand language.

Do not mechanically insert the phrase into every page or section.

The site itself should command attention through:

- Hierarchy
- Clarity
- Typography
- Composition
- Strong messaging
- Quality work
- Restraint

Using the slogan more often does not automatically make the site more on-brand.

## 4. Avoid obvious AI-design patterns

Do not default to:

- Purple/blue gradients
- Random glow effects
- Glass cards
- Excessive blur
- Decorative pills everywhere
- Huge collections of identical rounded cards
- Floating abstract blobs
- Arbitrary icons for every bullet
- Animated gradients
- Constant scroll animations
- Fake dashboards
- Meaningless metrics
- Generic smiling-office stock photography
- Oversized empty sections created only for visual drama

A section should have a reason to exist.

# Conversion Principles

## 1. Each page has a job

Before substantially restructuring a page, determine its primary objective.

Examples may include:

- Explain a service
- Establish trust
- Show work
- Answer pricing questions
- Generate a project inquiry
- Encourage a call
- Provide useful educational content
- Capture website-audit interest

Every major section should help the visitor:

- Understand
- Trust
- Evaluate
- Act

If it does none of those things, question whether it belongs.

## 2. One dominant action

Important pages should have a clear primary CTA.

Secondary actions may exist, but they should not visually compete with the primary objective.

Do not add buttons simply because there is available space.

Use descriptive CTA language whenever possible.

Prefer:

- Start a Project
- Book a Call
- View the Work
- Audit Your Website
- Tell Us About Your Project

over vague labels such as:

- Submit
- Click Here
- Explore
- Learn

unless the context makes the action obvious.

## 3. Do not optimize for clicks at the expense of qualified leads

Veriq does not need every visitor.

Messaging should help the right customer understand:

- What Veriq does
- Who the service is for
- What level of work to expect
- What the next step is

Pricing, positioning, and service descriptions should qualify customers rather than deliberately hiding useful information merely to increase form submissions.

# Copy and Voice

## Veriq's voice

Write in a way that is:

- Direct
- Confident
- Human
- Specific
- Clear
- Useful
- Professional without sounding corporate
- Conversational without sounding sloppy
- Knowledgeable without pretending to know everything

The writing should feel like it came from the person actually running the business, not from a generic marketing-copy generator.

## Avoid

Do not use empty agency language such as:

- Elevate your digital presence
- Unlock your potential
- Cutting-edge solutions
- Innovative solutions tailored to your needs
- In today's digital landscape
- Transform your online presence
- We leverage cutting-edge technology
- Seamless digital experiences
- Results-driven solutions

Avoid:

- Excessive em dashes
- Repetitive three-item rhetorical patterns
- Unnecessary rhetorical questions
- Overexplaining simple ideas
- Fake urgency
- Overuse of exclamation points
- Corporate filler
- SEO copy that humans would never naturally say
- Repeating the same value proposition in every section

## Narrative consistency

Do not casually switch between:

- I
- we
- Veriq
- our team

Preserve the established narrative style of the surrounding page unless the user requests a broader voice change.

Veriq should never imply a larger staff, office, client roster, or organizational scale than confirmed information supports.

## Existing approved copy

Do not rewrite strong existing copy merely to make it different.

Make copy changes when they improve:

- Clarity
- Accuracy
- Conversion
- Hierarchy
- Brand consistency
- Search usefulness
- Readability

Not because Codex can generate another version.

# Truthful Marketing

Veriq must not fabricate credibility.

Never invent or imply:

- Clients
- Customer results
- Revenue generated
- Leads generated
- Conversion improvements
- Search rankings achieved
- Review counts
- Testimonials
- Awards
- Certifications
- Years of agency history
- Team size
- Partnerships
- Guarantees
- Availability promises
- Response-time promises
- Pricing
- Discounts
- Limited-time offers
- Scarcity

Do not write "trusted by businesses across..." without evidence.

Do not write "proven results" unless actual results are being shown.

## Portfolio and work

Real client work and concept/demo work must be represented honestly.

Do not:

- Present concept work as a paying client
- Invent testimonials for portfolio projects
- Invent performance results
- Invent project outcomes
- Invent business-owner quotes
- Imply a redesign was commissioned when it was speculative

A strong concept can still demonstrate design ability without pretending to be something it is not.

# Pricing

Pricing is business-sensitive information.

Do not invent:

- Starting prices
- Package prices
- Discounts
- Deposits
- Payment schedules
- Monthly fees
- Maintenance rates
- Financing
- Promotional offers

Use only pricing explicitly confirmed by the user or already intentionally implemented as current pricing.

When displaying starting prices, preserve the distinction between:

- A starting point
- A typical project
- A fixed package price
- A custom quote

Do not accidentally convert "starting at" pricing into a promise that every project at that level receives a fixed list of deliverables.

Pricing pages should educate and qualify customers, not use manipulative fake anchors or fake discounts.

# Services

Keep service positioning focused.

Do not expand Veriq's service list merely because an adjacent service sounds marketable.

Publicly presented capabilities should reflect work Veriq can actually deliver.

When adding or rewriting a service page:

1. Define the problem.
2. Explain the service clearly.
3. Explain what makes Veriq's approach useful.
4. Provide enough detail for a buyer to evaluate the service.
5. Give the visitor an obvious next step.

Do not create thin service pages solely to target keyword variations.

# Work / Portfolio

The work section is one of Veriq's strongest forms of proof.

Prioritize:

- Strong visual presentation
- Clear project context
- Honest project type
- Useful explanation of the design/problem
- Screenshots that actually demonstrate quality

Avoid burying the work beneath excessive agency copy.

As real client work is added, structure the system so real case studies can gradually become stronger proof than concept work.

# Blog / Resources

Veriq content should exist because it is useful, not because the site needs more URLs.

Articles should:

- Answer a real question
- Demonstrate actual knowledge
- Be specific
- Have a clear point
- Offer useful examples when appropriate
- Sound human
- Be edited enough that the author could comfortably put their name on it

Do not produce scaled batches of generic SEO articles.

Do not create near-duplicate posts targeting small keyword variations.

Avoid articles that merely summarize obvious information available everywhere else.

Do not stuff "Des Moines web design" or similar phrases unnaturally into blog posts.

# Local SEO

Veriq has a real local-market focus, so local relevance should be represented naturally.

Preserve clear signals around Des Moines where useful, especially on pages with local commercial intent.

Do not turn the site into local-keyword spam.

Avoid:

- Repeating "Des Moines web design" unnaturally
- Creating separate pages for every synonym of web design
- Creating thin suburb doorway pages
- Creating location pages for places Veriq does not genuinely serve
- Stuffing headings with exact-match phrases
- Duplicating service content solely for another keyword

Prefer:

- One strong page per meaningful search intent
- Natural geographic context
- Strong internal linking
- Useful service information
- Real work
- Real business information
- Consistent entity information

# SEO Standards

For relevant pages, verify intentional:

- Title metadata
- Meta descriptions
- Canonicals where appropriate
- Open Graph/social metadata
- Semantic heading hierarchy
- Internal links
- Useful alt text
- Sitemap inclusion
- Robots behavior
- Structured data

Do not add schema merely because a schema type exists.

Structured data must reflect visible, truthful business information.

Do not make major SEO architecture changes as part of unrelated visual work.

# Responsive Design

Responsive quality is mandatory.

The site must work at:

- Small phones
- Larger phones
- Tablets
- Small laptops
- Desktop
- Large desktop

Do not optimize only for 1440px and 390px.

Pay particular attention to:

- Navigation
- Large condensed headings
- Hero compositions
- Image cropping
- Pricing layouts
- Work/project cards
- Carousels
- Forms
- CTA groups
- Sticky/fixed elements
- Footer layout
- Horizontal overflow
- Tablet widths

Never solve one breakpoint by carelessly breaking another.

# Accessibility

Accessibility is part of design quality.

At minimum preserve:

- Semantic HTML
- Logical heading order
- Useful link/button labels
- Form labels
- Helpful validation
- Keyboard navigation
- Visible focus states
- Sufficient contrast
- Appropriate alt text
- Reduced-motion handling for substantial motion

Do not remove focus indicators for aesthetic reasons.

Do not put essential information exclusively inside animation, hover states, or imagery.

# Animation and Interaction

Motion should reinforce the brand, not become the brand.

Use animation when it improves:

- Hierarchy
- Feedback
- Navigation
- Orientation
- Visual polish

Avoid:

- Animating every section on scroll
- Long entrance delays
- Excessive parallax
- Continuous distracting motion
- Motion that makes the site feel like a design demo
- Interaction that harms usability on touch devices

Respect `prefers-reduced-motion` when appropriate.

# Images and Assets

Prefer imagery that strengthens the actual Veriq brand or demonstrates the work.

For website screenshots and mockups:

- Keep the website legible enough to function as proof
- Preserve device/image focal points responsively
- Use high-quality exports
- Avoid visibly stretched screenshots
- Avoid fake UI artifacts
- Avoid using mockups so heavily that users cannot see the actual design work

Keep filenames understandable.

Use framework-native image optimization where practical.

Do not add stock imagery merely because a section feels empty.

# Forms, Leads, and Integrations

Forms are production functionality.

Do not alter:

- Submission recipient
- API routes
- Email routing
- CRM/integration behavior
- Spam-prevention logic
- Analytics events
- Environment variables

unless the task requires it.

Never commit secrets.

Use environment variables for secrets and environment-specific values.

Preserve validation and spam protection.

If form behavior changes, test:

- Successful submission
- Required fields
- Invalid input
- Failure behavior
- Loading state
- Success state
- Duplicate submission behavior where relevant

# Analytics and Tracking

Do not remove or replace existing analytics/tracking implementations casually.

Do not invent tracking IDs.

When adding meaningful conversion points, consider whether existing analytics conventions should track them.

Avoid collecting unnecessary user information.

# Engineering Principles

## Inspect before editing

Do not begin a meaningful implementation based only on the prompt.

Inspect:

- Relevant route
- Components
- CSS/modules
- Shared layout
- Existing utilities
- Data sources
- Config
- Package scripts

first.

## Make the smallest coherent change

Prefer targeted implementation over broad refactoring.

Do not:

- Rewrite unrelated components
- Introduce a new design system for one page
- Replace working architecture for stylistic preference
- Convert styling approaches without a clear reason
- Add libraries for trivial functionality
- Upgrade framework versions during unrelated tasks
- Reformat the entire repository

## Reuse established systems

Before creating something new, look for existing:

- Buttons
- Containers
- Section patterns
- Navigation components
- Form controls
- Typography utilities
- CTA sections
- Card treatments
- Responsive helpers
- Animation utilities

Reuse when it creates consistency.

Do not force reuse when an existing component genuinely does not fit the new requirement.

## Server/client boundaries

Keep client-side JavaScript purposeful.

Prefer the repository's existing rendering patterns.

Do not turn server-renderable content into client components without a reason.

Avoid adding hydration and dependencies for effects achievable with HTML/CSS.

## Dependencies

Prefer existing dependencies.

Do not install packages for:

- Simple icons
- Basic animation
- Trivial formatting
- Utility functions easily implemented with existing tools

If a new dependency is genuinely justified, explain why.

# Repository Hygiene

Do not make unrelated changes.

Do not:

- Replace lockfiles unnecessarily
- Commit generated build artifacts
- Commit temporary screenshots
- Leave debug logging
- Leave commented-out experiments
- Leave unused imports
- Leave dead experimental components from the task
- Rename large sets of files without reason
- Change deployment settings casually
- Alter domains or DNS
- Change production credentials
- Modify environment secrets

Keep the codebase easier to understand after the task than before it.

# Visual Review

For meaningful UI work, do not stop when the code compiles.

If preview/browser tooling is available, visually inspect representative widths.

Check:

- Overall composition
- Typography wrapping
- Section spacing
- Alignment
- Image crops
- CTA hierarchy
- Mobile stacking
- Tablet layout
- Navigation behavior
- Fixed/sticky elements
- Footer
- Horizontal overflow

A technically valid page can still be visually bad.

# Verification

Before finishing a meaningful task:

1. Review the complete diff.
2. Confirm the change matches the requested scope.
3. Check for accidental unrelated edits.
4. Run the repository's applicable lint command.
5. Run type checking if available.
6. Run tests relevant to the change if available.
7. Run the production build when appropriate.
8. Fix issues introduced by the task.
9. Check obvious routes and links affected by the change.
10. Inspect responsive behavior when UI changed.
11. Report anything that could not be verified.

Do not claim a test passed if it was not run.

Do not hide pre-existing failures. Clearly distinguish:

- Errors introduced by the task
- Existing repository errors
- Checks that could not be run

# Definition of Done

A meaningful Veriq website task is complete when:

- The requested change is implemented
- It feels like Veriq
- It supports the page's actual purpose
- It does not introduce unsupported claims
- It does not make Veriq look cheaper, larger, or more established than reality
- Existing brand consistency is preserved
- Responsive behavior remains sound
- Accessibility has not been carelessly regressed
- SEO has not been carelessly regressed
- Production functionality remains intact
- Applicable validation passes or failures are clearly explained
- The diff contains no unnecessary scope creep

# Final Response Format

After implementation, provide a concise summary containing:

## Changed

- Major files/components changed
- What was implemented

## Verified

- Lint
- Typecheck
- Tests
- Build
- Responsive/browser checks

Only list checks that were actually performed.

## Notes

- Assumptions made
- Anything not verified
- Any remaining decision the user needs to make

Do not pad the final response with a long explanation of obvious changes.
